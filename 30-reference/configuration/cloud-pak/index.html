    Cloud Paks🔗

    Defines the Cloud Pak(s) which is/are layed out on the OpenShift cluster, typically in one or more OpenShift projects. The Cloud Pak definition represents the instance users connect to and which is responsible for managing the functional capabilities installed within the application.

    Cloud Pak configuration🔗

    • Cloud Pak for Data
    • Cloud Pak for Integration
    • Cloud Pak for Watson AIOps
    • Cloud Pak for Business Automation
    • IBM Bob self-hosted

    cp4d🔗

    Defines the Cloud Pak for Data instances to be configured on the OpenShift cluster(s).

    cp4d:
- project: cpd
  operators_project: cpd-operators
  openshift_cluster_name: sample
  cp4d_version: latest
  use_fs_iam: False
  change_node_settings: True
  db2u_limited_privileges: False
  ibm_cert_manager: False
  accept_licenses: False
  openshift_storage_name: nfs-storage
  cp4d_entitlement: 
  - cpd-enterprise
  # - cpd-standard
  # - cognos-analytics
  - data-product-hub
  # - datastage
  # - ikc-premium
  # - ikc-standard
  # - openpages
  # - planning-analytics
  # - product-master
  # - speech-to-text
  # - text-to-speech
  - watson-assistant
  # - watson-discovery
  # - watsonx-ai
  # - watsonx-code-assistant-ansible
  # - watsonx-code-assistant-z
  # - watsonx-data
  # - watsonx-gov-mm
  # - watsonx-gov-rc
  # - watsonx-orchestrate  
  cp4d_production_license: True
  state: installed
  
  cartridges:
  - name: cpfs
  - name: cpd_platform

    Properties🔗

    Property Description Mandatory Allowed values
    project Name of the OpenShift project of the Cloud Pak for Data instance Yes
    operators_project Name of the OpenShift project that holds the operators. If not specified, the name will be project-operators No Valid OpenShift project name
    openshift_cluster_name Name of the OpenShift cluster Yes, inferred from openshift Existing openshift cluster
    cp4d_version Cloud Pak for Data version to install, this will determine the version for all cartridges. When specifying latest, the version will be determined from the olm-utils image Yes latest, x.y.z
    sequential_install Deprecated property No True (default), False
    use_fs_iam If set to True the deployer will enable Foundational Services IAM for authentication No False (default), True
    use_cp_alt_repo When set to False, deployer will use use the alternative repo specified in cp_alt_repo resource No True (default), False
    change_node_settings Controls whether the node settings using the machine configs will be applied onto the OpenShift cluster. No True, False
    db2u_limited_privileges Depicts whether Db2U containers run with limited privileges. If they do (True), Deployer will create KubeletConfig and Tuned OpenShift resources as per the documentation. No False (default), True
    ibm_cert_manager Specify if the IBM certificate manager must be installed instead of the Red Hat certificate Manager No False (default), True
    accept_licenses Set to 'True' to accept Cloud Pak licenses. Alternatively the --accept-all-licenses can be used for the cp-deploy.sh command No True, False (default)
    cp4d_entitlement Set to cpd-enterprise, cpd-standard, watsonx-data, watsonx-ai, watsonx-gov-mm, watsonx-gov-rc, dependent on the deployed license, multiple entitlements can be specified No For valid values, refer to product documentation
    cp4d_production_license Whether the Cloud Pak for Data is a production license No True (default), False
    state Indicated whether Cloud Pak for Data must be installed or removed No installed (default), removed
    image_registry_name When using private registry, specify name of image_registry No
    openshift_storage_name References an openshift_storage element in the OpenShift cluster that was defined for this Cloud Pak for Data instance. The name must exist under `openshift.[openshift_cluster_name].openshift_storage. No, inferred from openshift->openshift_storage
    cartridges List of cartridges to install for this Cloud Pak for Data instance. See Cloud Pak for Data cartridges for more details Yes

    cp4i🔗

    Defines the Cloud Pak for Integration installation to be configured on the OpenShift cluster(s).

    cp4i:
- project: cp4i
  openshift_cluster_name: {{ env_id }}
  openshift_storage_name: nfs-rook-ceph
  cp4i_version: 2021.4.1
  accept_licenses: False
  use_top_level_operator: False
  top_level_operator_channel: v1.5
  top_level_operator_case_version: 2.5.0
  operators_in_all_namespaces: True
 
  instances:
  - name: integration-navigator
    type: platform-navigator
    license: L-RJON-C7QG3S
    channel: v5.2
    case_version: 1.5.0

    OpenShift projects🔗

    The immediate content of the cp4i object is actually a list of OpenShift projects (namespaces). There can be more than one project and instances can be created in separate projects.

    cp4i:
- project: cp4i
  ...

- project: cp4i-ace
  ...

- project: cp4i-apic
  ...

    Operator channels, CASE versions, license IDs🔗

    Before you run the Cloud Pak Deployer be sure that the correct operator channels are defined for the selected instance types. Some products require a license ID, please check the documentation of each product for the correct license. If you decide to use CASE files instead of the IBM Operator Catalog (more on that below) make sure that you selected the correct CASE versions - please refer: https://github.com/IBM/cloud-pak/tree/master/repo/case

    CP4I main properties🔗

    The following properties are defined on the project level:

    Property Description Mandatory Allowed values
    project The name of the OpenShift project that will be created and used for the installation of the defined instances. Yes
    openshift_cluster_name Dynamically defined form the env_id parameter during the execution. Yes, inferred from openshift Existing openshift cluster
    openshift_storage_name Reference to the storage definition that exists in the openshift object (please see above). The definition must include the class name of the file storage type and the class name of the block storage type. No, inferred from openshift->openshift_storage
    cp4i_version The version of the Cloud Pak for Integration (e.g. 2021.4.1) Yes
    use_case_files The property defines if the CASE files are used for installation. If it is True then the operator catalogs are created from the CASE files. If it is False, the IBM Operator Catalog from the entitled registry is used. No True, False (default)
    accept_licenses Set to True to accept Cloud Pak licenses. Alternatively the --accept-all-licenses can be used for the cp-deploy.sh command Yes True, False
    use_top_level_operator If it is True then the CP4I top-level operator that installs all other operators is used. Otherwise, only the operators for the selected instance types are installed. No True, False (default)
    top_level_operator_channel Needed if the use_top_level_operator is True otherwise, it is ignored. Specifies the channel of the top-level operator. No
    top_level_operator_case_version Needed if the use_top_level_operator is True otherwise, it is ignored. Specifies the CASE package version of the top-level operator. No
    operators_in_all_namespaces It defines whether the operators are visible in all namespaces or just in the specific namespace where they are needed. No True, False (default)
    instances List of the instances that are going to be created (please see below). Yes

    Warning

    Despite the properties use_case_files, use_top_level_operator and operators_in_all_namespaces are defined as optional, they are actually crucial for the way of execution of the installation process. If any of them is omitted, it is assumed that the default False value is used. If none of them exists, it means that all are False. In this case, it means that the IBM Operator Catalog is used and only the needed operators for specified instance types are installed in the specific namespace.

    Properties of the individual instances🔗

    The instance property contains one or more instances definitions. Each instance must have a unique name. There can be more the one instance of the same type.

    Naming convention for instance types🔗

    For each instance definition, an instance type must be specified. We selected the type names that are as much as possible similar to the naming convention used in the Platform Navigator use interface. The following table shows all existing types:

    Instance type Description/Product name
    platform-navigator Platform Navigator
    api-management IBM API Connect
    automation-assets Automation assets a.k.a Asset repo
    enterprise-gateway IBM Data Power
    event-endpoint-management Event endpoint manager - managing asynchronous APIs
    event-streams IBM Event Streams - Kafka
    high-speed-transfer-server Aspera HSTS
    integration-dashboard IBM App Connect Integration Dashboard
    integration-design IBM App Connect Designer
    integration-tracing Operations Dashboard
    messaging IBM MQ

    Platform navigator🔗

    The Platform Navigator is defined as one of the instance types. There is typically only one instance of it. The exception would be an installation in two or more completely separate namespaces (see the CP4I documentation). Special attention is paid to the installation of the Navigator. The Cloud Pak Deployer will install the Navigator instance first, before any other instance, and it will wait until the instance is ready (this could take up to 45 minutes).

    When the installation is completed, you will find the admin user password in the status/cloud-paks/cp4i--cp4i-PN-access.txt file. Of course, you can obtain the password also from the platform-auth-idp-credentials secret in ibm-common-services namespace.

    cp4waiops🔗

    Defines the Cloud Pak for Watson AIOps installation to be configured on the OpenShift cluster(s). The following instances can be installed by the deployer:

    • AI Manager
    • Event Manager
    • Turbonomic
    • Instana
    • Infrastructure management
    • ELK stack (ElasticSearch, Logstash, Kibana)

    Aside from the base install, the deployer can also install ready-to-use demos for each of the instances

    cp4waiops:
- project: cp4waiops
  openshift_cluster_name: "{{ env_id }}"
  openshift_storage_name: auto-storage
  accept_licenses: False
 
  instances:
  - name: cp4waiops-aimanager
    kind: AIManager
    install: true
  ...

    cp4ba🔗

    Defines the Cloud Pak for Business Automation installation to be configured on the OpenShift cluster(s).
    See Cloud Pak for Business Automation for additional details.

    ---
cp4ba:
- project: cp4ba
  collateral_project: cp4ba-collateral
  openshift_cluster_name: "{{ env_id }}"
  openshift_storage_name: auto-storage
  accept_licenses: false
  state: installed
  cpfs_profile_size: small # Profile size which affect replicas and resources of Pods of CPFS as per https://www.ibm.com/docs/en/cpfs?topic=operator-hardware-requirements-recommendations-foundational-services

  # Section for Cloud Pak for Business Automation itself
  cp4ba:
    # Set to false if you don't want to install (or remove) CP4BA
    enabled: true # Currently always true
    profile_size: small # Profile size which affect replicas and resources of Pods as per https://www.ibm.com/docs/en/cloud-paks/cp-biz-automation/latest?topic=pcmppd-system-requirements
    patterns:
      foundation: # Foundation pattern, always true - https://www.ibm.com/docs/en/cloud-paks/cp-biz-automation/latest?topic=deployment-capabilities-production-deployments#concept_c2l_1ks_fnb__foundation
        optional_components:
          bas: true # Business Automation Studio (BAS) 
          bai: true # Business Automation Insights (BAI)

    ibm_bob🔗

    Defines an IBM Bob self-hosted installation on an existing OpenShift cluster. The deployer installs IBM Bob with bobctl, which it takes from the versioned release bundle on GitHub. It downloads the bundle at run time, verifies its SHA-256 checksum and caches it in <status_dir>/downloads/ibm-bob/<version>/.

    ibm_bob:
- project: ibm-bob
  operators_project: ibm-bob-operators
  openshift_cluster_name: "{{ env_id }}"
  openshift_storage_name: odf-storage
  ibm_bob_version: 2.0.0
  accept_licenses: false
  reuse_existing_cert_manager: false
  state: installed
  premium_packages:
    rag: false
    z_proxy: false
    understand: false

    Prerequisites🔗

    The cluster requirements of IBM Bob (supported OpenShift versions, node architecture, storage, cert-manager and permissions) depend on the IBM Bob version. See the IBM Bob prerequisites. The deployer checks them before it installs.

    What the deployer does with them:

    • The file (RWX) and block (RWO) storage classes are resolved from the openshift_storage element that openshift_storage_name refers to.
    • If no cert-manager operator is found, the deployer installs the Red Hat cert-manager operator, as it does for Cloud Pak for Data. The IBM License Service is not installed.
    • The IBM entitlement key is read from the vault secret ibm_cp_entitlement_key. IBM Bob images are pulled from cp.icr.io with this key.

    Ingress certificate🔗

    By default, Bob generates its own self-signed CA and issues a certificate for its routes. The deployer saves the CA certificate to <status_dir>/ibm-bob/<project>/bob-ca.crt; distribute it to every workstation that connects to IBM Bob.

    To provision a publicly trusted certificate automatically, add an ingress_cert block with exactly one of:

    Key Description
    acme_email Email address for ACME HTTP-01 (Let's Encrypt by default). The deployer creates a namespace-scoped cert-manager Issuer and a Certificate covering Bob's three routes, waits for Ready, and calls bobctl setup-route. The cluster's apps domain must be reachable from the internet for the HTTP-01 challenge.
    cluster_issuer Name of an existing cert-manager ClusterIssuer. The deployer creates the Certificate only; the ClusterIssuer must already be Ready.

    acme_email and cluster_issuer are mutually exclusive. The optional acme_url key overrides the ACME directory URL (defaults to Let's Encrypt production; set to a staging or corporate ACME CA as needed).

    # ACME HTTP-01 — Let's Encrypt (default) or corporate ACME CA
ibm_bob:
- project: ibm-bob
  ...
  ingress_cert:
    acme_email: ops@example.com
    # acme_url: https://acme-v02.api.letsencrypt.org/directory   # default

# Existing ClusterIssuer
ibm_bob:
- project: ibm-bob
  ...
  ingress_cert:
    cluster_issuer: my-corporate-issuer

    Bob's route hostnames (covered by the certificate):

    • bob.<project>.<apps-domain>
    • api.bob.<project>.<apps-domain>
    • bob-keycloak.<project>.<apps-domain>

    On state: removed, the deployer deletes the Certificate and, if ACME mode was used, the Issuer created by the deployer. The secret bob-cluster-ingress-tls is deleted together with the Bob namespace.

    Model gateway🔗

    If model_gateway is specified, the deployer writes it to model-gateway.yaml in the status directory and passes it to bobctl install --model-config. If it is omitted, IBM Bob is installed with an empty model gateway configuration, which you can set later with bobctl update-model-config. The structure of model_gateway follows the IBM Bob model gateway configuration.

    Do not put secrets in the configuration. Refer to them as env.<VAR> and map each <VAR> to a vault secret:

      model_gateway:
    models:
    - model_name: premium-ide
      openai_compatible:
        api_key: env.AZURE_API_KEY
  model_gateway_secret_names:
    AZURE_API_KEY: ibm-bob-azure-api-key

    ./cp-deploy.sh vault set -vs=ibm-bob-azure-api-key=<value>

    The deployer reads the values from the vault when it installs, and removes the temporary files that contain them afterwards.

    Air-gapped installation🔗

    For air-gapped clusters, set CPD_AIRGAP=true and provide an image_registry object with the private registry that holds the mirrored IBM Bob images. Set image_registry_name in the ibm_bob object to reference it.

    Mirror the images before running the deployer:

    # Step 1: download images from cp.icr.io to a local filesystem directory
CPD_AIRGAP=false CPD_SKIP_PORTABLE_REGISTRY=false \
  ./cp-deploy.sh env download -c <config-dir> -l <status-dir>

# Step 2: upload from the filesystem directory to the private registry
CPD_AIRGAP=true CPD_SKIP_PORTABLE_REGISTRY=false \
  ./cp-deploy.sh env download -c <config-dir> -l <status-dir>

    Or mirror directly from the IBM registry to the private registry in one step:

    CPD_AIRGAP=false CPD_SKIP_PORTABLE_REGISTRY=true \
  ./cp-deploy.sh env download -c <config-dir> -l <status-dir>

    Store the private registry credentials in the vault before running the apply:

    ./cp-deploy.sh vault set -vs=image-registry-<name>=<user>:<password>

    Then run the deployer with CPD_AIRGAP=true:

    CPD_AIRGAP=true ./cp-deploy.sh env apply -c <config-dir> -l <status-dir>

    Uninstall🔗

    To remove an IBM Bob instance, set state: removed. No storage or license properties are required:

    ibm_bob:
- project: ibm-bob
  openshift_cluster_name: "{{ env_id }}"
  ibm_bob_version: 2.0.0
  state: removed

    The deployer deletes the Bob CR, removes the Helm release, deletes both namespaces (project and operators_project) and removes the Keycloak admin vault key. cert-manager is left untouched.

    Access information🔗

    When the installation has completed, the smoke tests wait for the operators and the Bob custom resource to be ready. They then write the following to <status_dir>/cloud-paks/cloud-pak-deployer-info.txt, which is also displayed at the end of the run:

    • The gateway URL for IBM Bob clients (BOB_GATEWAY_URL for bob-shell, gatewayUrl for bob-ide).
    • The Keycloak URL, admin user and password (also stored in the vault as ibm_bob_keycloak_admin_<project>_<cluster>).
    • The URLs for premium packages (RAG URL, Internal search URL, Z Proxy URL, Z Lookup URL), if enabled and available in the Bob custom resource status.
    • When the default self-signed certificate is in use: the CA certificate is saved as <status_dir>/ibm-bob/<project>/bob-ca.crt. Distribute it to every workstation that connects to IBM Bob, because it is not publicly trusted.
    • When ingress_cert is configured: confirmation that the cert-manager certificate was issued and registered, including the hostnames it covers.

    Adding users🔗

    After installation, add users through the IBM Bob Admin UI at https://bob.<project>.<apps-domain>/admin. Log in with the temp-admin Keycloak credentials from the access information above. Navigate to Users & Teams, add each user by email address, assign their role (bob-admin or bob-user), and add them to a team.

    Alternatively, add users directly in the Keycloak Admin Console at https://bob-keycloak.<project>.<apps-domain>: create a user in the bob realm, set a password, and assign the bob-admin or bob-user realm role.

    Post-installation tasks🔗

    Tasks such as LDAP and IDP configuration and customer-provided TLS certificates are performed with bobctl. See Post-installation tasks.

    OpenShift AI model serving🔗

    Instead of writing a model_gateway block by hand, the deployer can serve one of the open-weight models listed under Supported models on Red Hat OpenShift AI (KServe + vLLM) and generate the Bob model gateway configuration automatically. Configure this with openshift_ai_models in the ibm_bob object. openshift_ai_models and model_gateway are mutually exclusive.

    What IBM Bob supports and requires for these models is documented only in the IBM Bob documentation: Required and supported models and Recommended vLLM runtime configuration. Check these pages before you choose a model.

    ibm_bob:
- project: ibm-bob
  ...
  openshift_ai_models:
    core_model: nemotron-3-ultra       # see Supported models
    quantization: fp8                  # default depends on the model, see Supported models
    guardrail_model: openai/gpt-oss-20b  # default; configurable
    project: ibm-bob-models            # namespace for ServingRuntime / InferenceService / PVCs
    gpus_per_core_model: 8             # default depends on the model, see Supported models
    gpus_per_guardrail_model: 1
    storage_size:
      core: 700Gi                      # default depends on the model and quantization
      guardrail: 60Gi
    # runtime_image:                   # vLLM image per inference service
    #   core: vllm/vllm-openai:v0.32.0
    #   guardrail: vllm/vllm-openai:v0.32.0
    # huggingface_token_secret_name: ibm-bob-huggingface-token
    # vllm_extra_args: []
    # skip_gpu_check: false

    The openshift object must have openshift_ai.install: auto (or True) and gpu.install: auto (or True). The deployer installs OpenShift AI and the NFD + NVIDIA GPU operators automatically when both are set to auto.

    openshift_ai_models properties🔗

    Property Description Mandatory Allowed values
    core_model Core model to serve. Exactly one may be configured. Yes core_model value in Supported models
    quantization Weight quantization variant. Not all variants are available for all models. No Quantizations in Supported models; default per model
    guardrail_model Model ID for the guardrail (safety) model served on the security and background slots. No default openai/gpt-oss-20b
    project OpenShift namespace for the model serving objects (PVCs, ServingRuntimes, InferenceServices). No default <ibm_bob.project>-models
    gpus_per_core_model Number of GPUs requested by the core model InferenceService. The vLLM --tensor-parallel-size is set to the same number. No default per model, see Supported models
    gpus_per_guardrail_model Number of GPUs requested by the guardrail model InferenceService. No default 1
    storage_size.core PVC size for the core model weights (and draft model, if any). No default per model and quantization, see Supported models
    storage_size.guardrail PVC size for the guardrail model weights. No default 60Gi
    runtime_image.core vLLM container image for the core model ServingRuntime. By default the deployer uses vllm/vllm-openai:v0.32.0 and automatically mirrors it to your private registry for air-gapped installations. Use this property to override the image with a custom build or different version. No default vllm/vllm-openai:v0.32.0
    runtime_image.guardrail vLLM container image for the guardrail model ServingRuntime. By default the deployer uses vllm/vllm-openai:v0.32.0 and automatically mirrors it to your private registry for air-gapped installations. No default vllm/vllm-openai:v0.32.0
    huggingface_token_secret_name Vault secret name for the Hugging Face access token. Required for gated model repositories. Used during env download in both connected and air-gapped mode. No vault secret name
    vllm_extra_args Extra vLLM CLI arguments appended to the arguments the deployer sets for the chosen model, so they take precedence. No list of strings
    skip_gpu_check Skip the GPU capacity check. The model pods will be Pending until GPU nodes are added. Use for deployer flow testing on clusters without GPUs. No True, False (default)

    Supported models🔗

    The Cloud Pak Deployer currently supports the following core models. For what IBM Bob requires of these models, see the IBM Bob documentation.

    core_model Quantization Hugging Face repository Default GPUs Default storage_size.core
    nemotron-3-ultra fp8 (default) RedHatAI/NVIDIA-Nemotron-3-Ultra-550B-A55B-FP8-dynamic 8 700Gi
    nemotron-3-ultra nvfp4 RedHatAI/NVIDIA-Nemotron-3-Ultra-550B-A55B-NVFP4 8 400Gi
    nemotron-3.5-super nvfp4 (default, only) nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4 2 100Gi
    laguna-s-2.1 fp8 (default) poolside/Laguna-S-2.1-FP8 8 150Gi
    laguna-s-2.1 nvfp4 poolside/Laguna-S-2.1-NVFP4 8 120Gi
    mistral-medium-3.5 fp8 (default, only) mistralai/Mistral-Medium-3.5-128B 8 300Gi

    The guardrail model openai/gpt-oss-20b serves the security and background gateway slots (1 GPU, 60Gi).

    The vLLM arguments are the values recommended on the IBM Bob vLLM page. nemotron-3.5-super is not on that page; its arguments are from the Hugging Face model card (2x H100 or 1x H200 recipe, so gpus_per_core_model: 1 is also valid on an H200). Adjust the arguments for your hardware with vllm_extra_args. The following notes are specific to the deployer:

    • The Laguna S 2.1 and Mistral Medium 3.5 speculative decoding draft models (dFlash and Eagle) are downloaded together with the model weights into a sub-directory of the model PVC. The Nemotron models use built-in speculative decoding.
    • The nvfp4 quantization of Laguna S 2.1 runs on NVIDIA Blackwell GPUs only. If vLLM crashes with DFlash at the default sequence limit, add --max-num-seqs=32 to vllm_extra_args.
    • All models are served with the upstream vllm/vllm-openai:v0.32.0 image (or the image configured via runtime_image). The vLLM images that Red Hat ships with OpenShift AI are not used because they contain older vLLM versions than these models need. In an air-gapped environment, the deployer automatically mirrors the runtime image, and the ubi9/ubi image of the temporary pods that load the model weights, to your private registry alongside the IBM Bob images during env download.

    What the deployer does🔗

    env download (both modes):

    1. Downloads model weights from Hugging Face into status_dir/downloads/ibm-bob/<version>/models/ using the hf CLI (huggingface_hub). A local marker file makes re-runs a no-op. The status directory is packaged by env download and carried to the air-gapped site.
    2. Mirrors the vLLM runtime container image (vllm/vllm-openai:v0.32.0 or user-configured runtime_image) and the registry.access.redhat.com/ubi9/ubi:latest image, which the temporary pods use to copy the model weights into the PVCs, to local disk (downloads/ibm-bob/<version>/images/vllm/) or directly to the private registry when image_registry_name is configured.

    env apply:

    1. Installs OpenShift AI (KServe) and the NFD + NVIDIA GPU operators when openshift_ai.install and gpu.install are auto.
    2. Creates a namespace and two PVCs (one per model) using the file storage class.
    3. In connected mode: runs a Kubernetes Job to download weights from Hugging Face directly into the PVCs.
    4. In air-gapped mode: copies weights from the local status directory into the PVCs file by file with oc cp (files already on the PVC with the same size are skipped, so an interrupted copy resumes; progress is written to <status_dir>/log/ibm-bob/models-copy-<core|guardrail>.log), then writes a PVC-side marker. If the local weights are missing (step 1 was not run), fails with instructions to run env download first.
    5. Creates a vLLM ServingRuntime and InferenceService per model with the recommended arguments (plus any vllm_extra_args).
    6. Waits for each InferenceService to have a resolvable URL, and for Ready status (unless skip_gpu_check is true).
    7. Renders the Bob model gateway config (slots premium-ide, security, background and a static router) and passes it to bobctl install --model-config.

    Vault token for Hugging Face🔗

    Set the token before running the deployer:

    ./cp-deploy.sh vault set -vs=ibm-bob-huggingface-token=<your-hf-token>

    Then reference it in the config:

      openshift_ai_models:
    core_model: nemotron-3-ultra
    huggingface_token_secret_name: ibm-bob-huggingface-token

    Air-gapped installation🔗

    The deployer follows the same two-phase pattern used for container images.

    Connected side — run env download:

    # Standard two-phase (status dir is packaged and carried to the air-gapped site)
CPD_AIRGAP=false ./cp-deploy.sh env download -c <config-dir> -l <status-dir>

# Direct air-gap (skip portable packaging, download and apply on same network path)
CPD_AIRGAP=false CPD_SKIP_PORTABLE_REGISTRY=true \
  ./cp-deploy.sh env download -c <config-dir> -l <status-dir>

    This downloads model weights (and Bob container images if image_registry_name is set) into <status-dir>/downloads/ibm-bob/<version>/models/. For gated models, set huggingface_token_secret_name first:

    ./cp-deploy.sh vault set -vs=ibm-bob-huggingface-token=<your-hf-token>

    Air-gapped side — carry the status dir and run env apply:

    For the standard two-phase flow, the status directory (which includes the downloaded weights) is packaged by env download and transferred to the air-gapped site. Then:

    CPD_AIRGAP=true ./cp-deploy.sh env apply -c <config-dir> -l <status-dir>

    The deployer copies the weights from the status directory into the cluster PVCs automatically. If the weights are not present (step 1 was skipped or the status dir was not carried over), the deployer fails with instructions.

    Testing without GPUs (skip_gpu_check)🔗

    To verify the deployer flow on a cluster without GPU nodes:

      openshift_ai_models:
    core_model: nemotron-3-ultra
    skip_gpu_check: true

    The deployer runs the full flow: OpenShift AI check, PVC creation, weight download (connected) or status-dir upload (air-gapped), ServingRuntime and InferenceService creation, gateway generation, and Bob installation. The model pods remain Pending as expected; this does not affect Bob itself. The same behavior applies in dry-run mode.

    Removal🔗

    When state: removed and openshift_ai_models is set, the deployer deletes the InferenceService and ServingRuntime objects. PVCs are kept — the downloaded weights are expensive to re-download. Delete them manually when no longer needed:

    oc delete pvc ibm-bob-core-model ibm-bob-guardrail-model -n ibm-bob-models
